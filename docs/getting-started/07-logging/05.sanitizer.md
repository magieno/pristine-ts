# The log sanitizer

A log is read by more people than a request is: it goes to a terminal, to a file, to an
aggregator, to Sentry. So a secret that reaches a log has left the place where it was
protected.

The framework itself logs the headers and the body of every request (the `[INBOUND REQUEST]`
and `[INBOUND RESPONSE COMPLETED]` lines), and your code logs objects it did not write. The
**log sanitizer** removes the secrets from every log before any logger gets it. It is on by
default.

> **You'll learn**
> - What is removed by default, and how a key or a value matches
> - How to block the secrets of your application, and allow a key that is not one
> - How to turn it off
> - What the sanitizer does not do

## Where it runs

In the `LogHandler`, one time for each log, before the fan-out to the loggers. The console
logger, the on-disk store and every external logger get the same clean log. You do not call
it yourself.

It never changes the objects you pass: a log often holds the live request, and your
application still uses it. The log gets a copy.

**It costs nothing for a log that nobody prints.** A debug log of the framework can hold a
whole dependency container. The message is sanitized at once (it is one string); the
highlights and the extra are sanitized the first time a logger reads them. A logger that
drops a log because of its severity reads nothing.

## The two rules

**By key.** The value under a sensitive key is replaced whole, whatever its type.

A key is compared without its case and without the characters that are not letters or
digits. It matches when it is one of the sensitive keys, or when it **ends** with one:

| Default sensitive key | Examples that match |
| --- | --- |
| `authorization` | `Authorization`, `proxy-authorization` |
| `cookie` | `Cookie`, `Set-Cookie` |
| `password`, `passwd`, `passphrase` | `password`, `userPassword`, `db_password` |
| `secret` | `client_secret`, `webhookSecret` |
| `token` | `access_token`, `refreshToken`, `x-auth-token`, `X-Amz-Security-Token` |
| `apikey` | `apiKey`, `x-api-key` |
| `privatekey` | `private_key` |
| `credentials` | `awsCredentials` |

`tokenCount` does not match: it does not end with `token`.

**By value.** Inside every string, the message included, what matches a sensitive pattern is
replaced. The defaults are a `Bearer` or `Basic` credential, and a JSON Web Token. This
catches a secret that sits in a URL, in a sentence or in an array of raw headers, where no
key names it.

```
before  {"requestHeaders": {"authorization": "Bearer eyJhbGciOi…", "host": "api.example.com"}}
after   {"requestHeaders": {"authorization": "[REDACTED]", "host": "api.example.com"}}

before  "Call failed: https://example.com/cb?id_token=eyJhbGciOi…&state=xyz"
after   "Call failed: https://example.com/cb?id_token=[REDACTED]&state=xyz"
```

## Block the secrets of your application

The framework cannot know that `pairingCode` is a secret in your application, or what your
own tokens look like. Name them:

```ts
await kernel.start(AppModule, {
  "pristine.logging.sanitizer.additionalSensitiveKeys": ["pairingCode", "ssn"],
  "pristine.logging.sanitizer.additionalSensitiveValuePatterns": ["sk_live_[A-Za-z0-9]+"],
});
```

or with environment variables:

```
PRISTINE_LOGGING_SANITIZER_ADDITIONAL_SENSITIVE_KEYS=pairingCode,ssn
PRISTINE_LOGGING_SANITIZER_ADDITIONAL_SENSITIVE_VALUE_PATTERNS=["sk_live_[A-Za-z0-9]+"]
```

In code a list is a list. In an environment variable it is a comma-separated string or a
JSON array of strings (see [Lists](../04-configuration/03.configuration-resolver.md#lists)).
Use the JSON array for patterns, because a regular expression often contains a comma.

## Allow a key that is not a secret

The block-list matches by the end of a key, so it also catches keys that only look like a
secret: `nextPageToken`, `tokenType`. Put them on the allow-list:

```ts
await kernel.start(AppModule, {
  "pristine.logging.sanitizer.additionalAllowedKeys": ["nextPageToken", "tokenType"],
});
```

```
PRISTINE_LOGGING_SANITIZER_ADDITIONAL_ALLOWED_KEYS=nextPageToken,tokenType
```

- **The allow-list wins** over the block-list.
- **An allowed key matches exactly** (without its case and punctuation). Allowing `token`
  does not allow `accessToken`: an exception is precise.
- **The value is still checked.** A JWT or a bearer credential under an allowed key is
  replaced: the value patterns apply to every string.

The framework allows one key by default, `controllerInstantiationToken`: it is a
dependency-injection token in the router's debug logs, the name of a class.

## Turn it off

One boolean:

```ts
await kernel.start(AppModule, {
  "pristine.logging.sanitizer.isActive": false,
});
```

```
PRISTINE_LOGGING_SANITIZER_IS_ACTIVE=false
```

The logs are then exactly what they were before the sanitizer existed: with the default
severity, the headers and the body of every request, as they came.

## Configuration

| Key | Default | Environment variable |
| --- | --- | --- |
| `pristine.logging.sanitizer.isActive` | `true` | `PRISTINE_LOGGING_SANITIZER_IS_ACTIVE` |
| `pristine.logging.sanitizer.sensitiveKeys` | the table above | `PRISTINE_LOGGING_SANITIZER_SENSITIVE_KEYS` |
| `pristine.logging.sanitizer.additionalSensitiveKeys` | none | `PRISTINE_LOGGING_SANITIZER_ADDITIONAL_SENSITIVE_KEYS` |
| `pristine.logging.sanitizer.allowedKeys` | `controllerInstantiationToken` | `PRISTINE_LOGGING_SANITIZER_ALLOWED_KEYS` |
| `pristine.logging.sanitizer.additionalAllowedKeys` | none | `PRISTINE_LOGGING_SANITIZER_ADDITIONAL_ALLOWED_KEYS` |
| `pristine.logging.sanitizer.sensitiveValuePatterns` | `Bearer`/`Basic` credentials, JWT | `PRISTINE_LOGGING_SANITIZER_SENSITIVE_VALUE_PATTERNS` |
| `pristine.logging.sanitizer.additionalSensitiveValuePatterns` | none | `PRISTINE_LOGGING_SANITIZER_ADDITIONAL_SENSITIVE_VALUE_PATTERNS` |
| `pristine.logging.sanitizer.replacement` | `[REDACTED]` | `PRISTINE_LOGGING_SANITIZER_REPLACEMENT` |
| `pristine.logging.sanitizer.maximumDepth` | `12` | `PRISTINE_LOGGING_SANITIZER_MAXIMUM_DEPTH` |

`sensitiveKeys`, `allowedKeys` and `sensitiveValuePatterns` **replace** the defaults. To keep
the defaults and add to them, use the three `additional…` keys. `LogSanitizerDefaults` exports the default
lists.

## Pitfalls

- **It knows keys and shapes, not meaning.** A secret under a key such as `value` or `data`,
  with no recognizable shape, is not removed. Name the keys of your application.
- **A whole value goes.** An object under `credentials` becomes `[REDACTED]`, its harmless
  fields too. That is the safe side.
- **What is too deep is replaced, not kept.** Below `maximumDepth` the sanitizer writes
  `[REDACTED: too deep]`. Keep `maximumDepth` at or above your deepest
  `log…DepthConfiguration`.
- **A very large log is cut.** One log is limited to 20,000 values. What is beyond becomes
  `[REDACTED: too large]`. A log is for a person to read.
- **A pattern that does not compile is ignored**, with one line on stderr at start. Read
  that line: the pattern protects nothing.
- **If the sanitizer itself fails, the data of the log is dropped** and the message goes
  out alone. A raw log never gets through.
- **It covers logs.** A value you put in a trace attribute or in an error response is not a
  log; the sanitizer does not see it.
- **Turning it off brings the leak back.** With `isActive: false`, at the default severity,
  the `Authorization` header of every request is in your logs.
